00

Hazırlık

Bu bölüm yalnızca bir kez yapılır. Sonraki her deploy doğrudan Faz 01'den başlar.

1

Repoyu GHES'e taşı (ilk clone)

Bu repo şu an yalnızca github.com/bbatus/core-processing-backend'de. EP ile aynı akış: GHES (github.vpara.local) tarafında yeni bir repo açılıp içerik oraya taşınır.

Elle

GHES'te core-processing-backend adında boş bir repo oluşturun (organizasyon: EP'nin bulunduğu aynı org). Ardından bu makineden:

GHES'i ikinci remote olarak ekle ve pushla
cd ~/Documents/Projects/core-processing-backend
git remote add ghes git@github.vpara.local:<org>/core-processing-backend.git
git remote -v

git push ghes main
SSH zaten kuruluysa

EP için daha önce SSH anahtarı oluşturduysanız (~/.ssh/id_ed25519) aynı anahtar GHES için de kullanılabilir — GHES hesabınıza aynı açık anahtarı Settings → SSH and GPG keys'ten ekleyin. Yeniden anahtar üretmenize gerek yok.

.github/workflows/ push kısıtı

GitHub/GHES, .github/workflows/ altındaki dosyaların salt HTTPS+PAT ile (token'da workflow scope'u yoksa) push edilmesini reddeder. SSH ile push ederken bu kısıt yoktur — yukarıdaki komut bu yüzden SSH remote kullanıyor.

2

GHES Actions secrets/vars & runner erişimi — DOĞRULA

EP'nin pipeline.yml'i çalışıyor diye CPB'ninki de otomatik çalışacağı garanti DEĞİL — bu, bu runbook'un yazıldığı ortamdan doğrulanamayan tek adımdır.

Elle — kontrol şart
Neden garanti değil

EP'nin pipeline.yml'i vars.OPENSHIFT_SERVER_TST, secrets.OPENSHIFT_TEST_PASSWORD, secrets.REGISTRY_LOGIN_TOKEN, secrets.SONAR_TOKEN, secrets.FORTIFY_TOKEN, secrets.MEND_PROXY_PASSWORD gibi değerleri okuyor. Bunlar GHES'te Organizasyon seviyesinde tanımlıysa (ve bu repo'yla paylaşılıyorsa) otomatik gelir. Repo seviyesinde yalnızca EP'ye özel tanımlandıysa, CPB'de bunlar boş gelir ve ilgili job (build-and-deploy, mend-scan, fortify-scan, sonar-scan) ilk çalıştırmada patlar.

GHES web arayüzünden kontrol edin: Organization Settings → Secrets and variables → Actions — aşağıdaki isimlerin "Repository access" listesinde core-processing-backend'in de olduğunu (ya da "All repositories" seçili olduğunu) doğrulayın.

4

CPB'ye özgü config/flow/secret'ı OpenShift'te oluştur

Bu 3 kaynak pipeline tarafından asla uygulanmaz — bir kez elle oluşturulur, bağımsız yaşarlar (EP'deki aynı kural).

Elle
a) ConfigMap + kill-switch ConfigMap
oc login https://api.tst-vcloud.vpara.local:6443 -u srvc.vpara.vpaitst
oc project vepas-ai-am

oc apply -f k8s/configmap.yaml
oc apply -f k8s/configmap-flow.yaml
AI_AGENT_BASE_URL şu an placeholder

k8s/configmap.yaml'daki AI_AGENT_BASE_URL: "https://CHANGE_ME.example.internal/api/v1" değeri Didar ekibinin gerçek URL'i gelene kadar olduğu gibi bırakılabilir — bu deploy'u ENGELLEMEZ. Liveness/readiness AI Agent'a hiç dokunmaz, yalnızca DB'ye bakar. Tek etkisi: FLOW_AI_CALL_ENABLED=true kalırsa her dispatch denemesinde 3 kez başarısız HTTP çağrısı + log gürültüsü olur — bkz. Adım 7'deki öneri (FLOW_AI_CALL_ENABLED=false ile başlatın).

b) Secret — yalnızca 1 değer (AI_AGENT_API_KEY)
# Gercek deger yoksa (Didar henuz vermedi) gecici bos/dummy bir deger yeterli —
# FLOW_AI_CALL_ENABLED=false oldugu surece hic kullanilmaz.
AI_AGENT_API_KEY="dummy-not-yet-provided" envsubst < k8s/secret.yaml | oc apply -f -
DB_PASSWORD burada YOK

k8s/secret.yaml kasıtlı olarak yalnızca AI_AGENT_API_KEY içerir — DB kimlik bilgisi EP'nin genaiops-event-processor-secret'ından gelir (K2, tek DB kimliği).

5

Push et, Actions'ı izle

Her push build-test-scan'i (+ paralel mend-scan/fortify-scan/sonar-scan) çalıştırır; imaj + deploy yalnızca development/main ya da v* tag'inde.

Otomatik
bash
git push ghes main
  • build-test-scan — mvn -B clean test -Dtest='!*IntegrationTest'; Testcontainers testleri (2026-09-04'te gerçek Docker'da 53/53 yeşil doğrulandı) CI'da çalışmaz — self-hosted runner'da Docker soketi yok, EP'deki aynı kısıt.
  • mend-scan / fortify-scan / sonar-scan — EP'den kopyalanan reusable workflow'lar; fortify_blocker="0"/sonar_blocker="false", yani bulgu bulsalar bile pipeline'ı henüz kırmazlar.
  • build-and-deploy — imajı derler, containers.github.vpara.local'e pushlar, ardından OpenShift'e deploy eder.

Faz 00 Adım 2'yi atlamadıysanız buraya kadar gelmiş olmanız, GHES secrets/runner erişiminin sorunsuz olduğu anlamına gelir. Atladıysanız ve iş burada patlarsa önce oradan başlayın — kodla ilgisi olmayabilir.

Bu faz bekletilebilir. Faz 00-03 tamamlanmış CPB, AI Agent olmadan da OCP'de sağlıklı, boşta bekleyen bir pod olarak durur. Bu faz yalnızca gerçek URL elinize geçtiğinde uygulanır.

Gerçek URL'i ve API key'i yaz, bayrağı aç

3 komut, pod restart gerektirir.

Elle
bash
oc patch configmap core-processing-backend-config --type merge \
  -p '{"data":{"AI_AGENT_BASE_URL":"<Didar-ekibinin-verdigi-gercek-URL>"}}'

oc rollout restart deployment/core-processing-backend
oc rollout status deployment/core-processing-backend --timeout=300s
oc logs -f deploy/core-processing-backend
Auth şeması netleşmediyse (§14-S3)

AiAgentClientImpl API key'i Authorization: Bearer <key> header'ıyla gönderir (varsayım). Didar ekibi farklı bir şema (örn. özel header adı) isterse kodda tek satırlık bir değişiklik gerekir — bu runbook'un kapsamı dışı, `CPB_TASARIM_VE_GELISTIRME_PLANI` §14 açık sorular listesine bakın.

05

Fonksiyonel senaryo

EP zaten çalışıp gerçek bir R4 dispatch'i ürettiyse en doğal test budur. Gerçek bir R4 event'i beklemek istemiyorsanız aşağıdaki gibi elle bir ai_dispatch satırı seed edip de test edebilirsiniz (Docker simülasyonunda kullanılan aynı yöntem).

10

Uçtan uca doğrulama

EP'nin ürettiği (ya da elle seed edilen) bir dispatch'in CPB tarafından claim edilip AI Agent'a gittiğini, sonucun ai_action_inbox'a yazıldığını, EP'nin bunu alıp DCase'e uyguladığını izleyin.

Doğrula
izleme sorguları
-- CPB claim etti mi, tamamlandı mı
SELECT id, status, claimed_by, claimed_at FROM ai_dispatch ORDER BY id DESC LIMIT 5;

-- AI cagrisinin izi
SELECT * FROM ai_process ORDER BY id DESC LIMIT 5;
SELECT * FROM ai_interaction ORDER BY id DESC LIMIT 5;

-- CPB'nin uretttigi oneri EP'ye ulasti mi
SELECT id, action_type, status, requires_approval FROM ai_action_inbox ORDER BY id DESC LIMIT 5;

-- Iki servisin denetim izi birlikte (dogru sirada mi)
SELECT category, dcase_ticket_id, created_at FROM audit_log ORDER BY created_at DESC LIMIT 20;
Referans

Bu akışın tamamı 2026-09-02'de Docker'da (gerçek Kafka + gerçek Postgres + 2 WireMock) uçtan uca kanıtlandı — R4 önerisi → R5 human-feedback turu → kapanış, ~8 saniyede tamamlanmıştı. OCP'de aynı akışı görmeniz beklenir.
